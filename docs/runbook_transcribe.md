# 書き起こし手順書（定期実行・別モデル・別セッション向け）

PCの `C:\dev\claude\prospi-real\captures\<npb|wbc>\<Team>\` に置かれたスクリーンショットを、
1回の作業で1チームずつ `data/` に書き起こす手順。**この手順書の通りに進めれば、どのモデルでも
同じ品質になるように書いている。判断に迷う点は「迷ったとき」に従い、勝手に仕様を変えない。**

関連: `CLAUDE.md`（方針）、`docs/transcribe_guide.md`（1枚の読み方。サブエージェントが読む）、
`docs/data_schema.md`（JSONの定義）、`docs/grades.md`（等級）。

## 考え方（2026-10-04 見直し: 1チーム30分 → 数分、品質は同等以上）

- **LLMに画像を読ませるのは「選手画面を1人1回」だけ**。メニュー画面・切り替え途中のフレーム・
  完全に同じ画像は `src/prep_team.py` が画素で仕分ける（USAの正解ラベル103枚で全件一致）。
- **書き起こしはサブエージェントに並列で任せる**（1サブエージェント5枚まで）。メインの会話に
  選手画像を溜めないので、トークンも時間も大きく減る。
- **画素で確かめられるものは全部スクリプトで照合する**: 変化球の箱の位置（check_pitch_slots）、
  変化量（read_break）、特殊能力の行数とアイコンの色（check_abilities）、守備図の位置（check_fielding）、
  等級と数値の整合（validate）。書き起こし側には検出結果をヒントとして渡す。
- 読み取り画像の倍率は 1.5倍（1.0/1.5/2.0倍で同じ8人を書き起こし、精度差がないことを確認済み）。

## 絶対に守ること（2026-10-11 追加）

Brazil・Canada（2026-10-04）では、この手順のチェックを「画像がない」という誤った判断で飛ばし、
サブエージェントへの指示も書き換えた結果、変化量が仮置きの 4 のまま・箱の位置の誤り（11人）・
特殊能力の誤り（22人）・◎を○と読む誤りがコミットされ、2チームとも作り直しになった。
同じ画像・同じガイドで書き起こし直すと Haiku でも誤りは出なかったので、原因はモデルではなく手順の逸脱。

1. **サブエージェントへの指示は `jobs/<ジョブ名>.prompt.txt` の中身を一字一句そのまま渡す。**
   要約・言い換え・追記をしない。
2. **`python3 src/finalize_team.py <cat>/<team>` が終了コード 0（「完了条件を満たしました」）で終わるまで、
   そのチームの `data/` をコミットしない。** NG を残したままのコミット・push はしない。
3. 画像は `captures/`（PCから取り込んだもの）にある。「画像がないので照合は後で」と判断してはいけない。
   本当に見つからない場合は finalize_team.py が「元画像が見つかりません」と出すので、取り込みからやり直す。
4. 変化量の「第一パネルX段と第二パネルY段が不一致」のうち、**画素読み取りの構造的不一致**だけは
   完了判定をブロックしない（下の「4. チェック」参照。判定は finalize_team.py が画素から自動で行う）。
   自分の判断で unverified を付けてブロックを外したり、変化量を手で書き換えたりしない。

## 4. チェック（finalize_team.py が終了コード 0 になるまで直す）

```bash
python3 src/finalize_team.py wbc/<team>
```
1コマンドで、変化球の箱の位置 → 変化量の画素読み取りと書き込み → validate・変化量・特殊能力・守備図・
起用適性（◎○△ー）・元画像の有無の全チェック → NG 0 なら build_site.py まで行う。
- NG が出た選手だけ、その選手の `work/.../sheets/<元ファイル名>.png` を Read で見て `data/` の JSON を直し、
  もう一度 finalize_team.py を実行する。**エラーを消すために数値を都合よく変えない。**
  画像と食い違うのはデータ側の読み違い。
- 箱の位置を直すと、変化量は次の実行で自動的に画素から書き込まれる（変化量を手で書かない）。
- 何度直しても NG が残る選手がいたら、そのチームはコミットせず、残った NG を報告に書いて終える。

### 画素読み取りの構造的不一致について（2026-10-12 追加）

変化量の「第一パネルX段と第二パネルY段が不一致」は、データの値を変えても解消しない場合がある。
これはデータ側の読み違いではなく、第二パネルで該当する段の画素が点灯判定のしきい値（明るさ75・彩度20）に
わずかに届かないために起きる、画像固有の問題。G 等級など灰色に近い色の柄が第二パネルで暗く表示されると、
背景の灰色に近くなって起きる（Brazil の aparecido_23 シンキング・monteiro_59 チェンジアップで確認）。

**構造的な不一致と判断する条件（すべて満たすこと。finalize_team.py が画素から自動で判定する）:**
1. 問題が「第一パネルX段と第二パネルY段が不一致」だけで、X > Y（第二パネルが少なく読んでいる）。
2. 第一パネルの点灯段が根元から連続し（途中で途切れていない）、各段が背景（明るさ48〜52・彩度0〜2程度）より
   明確に高い（明るさ90以上、または彩度20以上）。
3. 第二パネルで読めなかった段も、背景に完全には同化していない。具体的には、同じ柄の確実に未点灯の段
   （X+2段目〜6段目）より彩度 +4 以上かつ明るさ +3 以上高い。
   ※ 固定の値で「背景より高い」を判定しないのは、正常な画像でも点灯段のすぐ次の段に色のにじみがあり、
   明るさ61・彩度16まで上がるため（USA・Australia の全投手で実測）。

この3条件を満たさない場合（例: 第一パネルも曖昧、第二パネルが背景と完全に同化している）は構造的な問題とみなさず、
通常どおり読み取りミス・箱位置の誤りを疑って調査する（finalize_team.py もブロックする）。

**構造的な不一致と判断した場合の扱い（finalize_team.py が自動で行う）:**
- 値は第一パネルの読み取り値を採用する。
- その選手の JSON に `"unverified": ["pitches[].break"]` を付け、`break_panel_mismatch` に球種・両パネルの段数・
  各段の画素値（明るさ/彩度）・判断根拠を記録する（`data/` には `notes` を残さない決まりなので、専用の項目に書く）。
  記録は実行のたびに画素から作り直す。条件を満たさなくなれば自動で外れる。
- この理由による `unverified` は、チームのコミットをブロックしない。finalize_team.py は「■ 画素読み取りが
  構造的に不一致だった箇所」として一覧に出し、終了コード 0 で終わる。
- 該当選手・該当球種は、実行の報告に必ず明記する（「画素読み取りが構造的に不一致だった箇所」として一覧化し、
  人の目視確認を促す）。

**この例外が適用されないもの（従来どおりブロックする）:**
- `check_pitch_slots.py` の箱位置の不一致
- `check_abilities.py` の特殊能力の行数・色の不一致
- `check_fielding.py` / `check_aptitude.py` の不一致
- `validate.py` の等級と数値の不整合
- `read_break.py` の「点灯段が途中で途切れている」「点灯段が0」（箱位置や order の誤りの可能性が高く、
  構造的な画素問題とは別物）
- 上の3条件を満たさない第一・第二パネルの不一致
- `merge_team.py` が出した「読み取りに自信がない箇所（notes）」も、その画像を見て確かめる。
  決められないものは報告に残す。

1. 改名コピーをPCへ: `python3 src/merge_team.py work/wbc/<team> --outputs /mnt/user-data/outputs/prospi-real`
   を実行すると（新しい結果がなくても）`work/.../commit_files.json` に一覧ができる。その中身をそのまま

   ※ merge を最後に実行したときの一覧なので、pass2 のあとに `--outputs` 付きで1回実行すればよい。
   続けて `python3 src/prep_team.py captures/wbc/<Team> --write-skipped` をもう一度実行する。元画像が処理済みに
   なったので、過去の実行で付いた綴り違いの古い改名コピー（例 `bieiera_49.png`）が「完全に同じ画像の重複」として
   `_skipped.json` に記録される（記録しないと、次回も同じチームが未処理として選ばれる。2026-10-12 Brazil で発生）。
2. GitHub（prospi-real、公開）: **直前の `finalize_team.py wbc/<team>` が終了コード 0 だったときだけ**、
   `data/` と `site/index.html` をコミットして push（ブランチは main）。
   **push 前に `git status --short` で `captures`・`work`・画像ファイルが含まれていないことを確認する。**
   拒否されたら `git pull --rebase` してから push。強制 push はしない。
   **403（access denied）で拒否されたら**、`add_repo`（access: push）を呼び直してからもう一度 push する。
   それでも push できなければ、作業が消えないように `git format-patch origin/main -o /mnt/user-data/outputs/prospi-real/_pending_push/`
   でパッチを作り、`device_commit_files` で PC の `C:\dev\claude\prospi-real\_pending_push\` に書き戻して、
   その旨を報告する（次の実行またはユーザーが適用できる。`_pending_push/` は .gitignore 済み）。
   **次の実行の最初に** PC の `_pending_push\` にパッチがあれば、それを取り込み `git am` で適用して push してから
   通常の手順に入る（push できたらPC側のパッチは消さず、報告で削除をお願いする）。

## 7. 報告（短く、日本語で）

- 処理したチームと追加人数（投手・野手の内訳）、スキップ枚数と理由の内訳
- 一覧にいるのに詳細画面がない選手
- 読み取りに自信がない箇所（選手・項目・読んだ値・理由）
- finalize_team.py の最終結果（「完了条件を満たしました」か、残った NG の一覧）
- 画素読み取りが構造的に不一致だった箇所（選手・球種・採用した段数・両パネルの画素値。人の目視確認を依頼する）
- GitHub への push の成否、残りのチーム数

## 迷ったとき

- 読めない値は推測で埋めず、いちばん近い読み値を入れて報告に載せる。
- スキーマにない情報が出てきたら、JSON に勝手なキーを足さずに報告する。
- テンプレート・CSS・スクリプトは定期実行では変更しない。画面のレイアウトや解像度が変わって
  スクリプトの座標が合わなくなった（チェックが大量にNGになる）場合は、無理に直さず報告する
  （`src/layout.py` に新しいレイアウトの切り出し位置を足す作業が必要）。
